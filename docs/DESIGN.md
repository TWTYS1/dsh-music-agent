# dsh-music-agent 技术设计

> 状态：生效中　|　最后更新：2026-08-25
> 本文是开发依据。任何偏离本文的实现都应先改本文，再改代码。

## 1. 产品定位

**以乐理教学为主轴、真实曲库作素材、记忆归用户的中文音乐学习伴侣。**

这句话里每个限定词都有排除意义：

| 限定 | 排除了什么 | 依据 |
|---|---|---|
| 乐理教学为主轴 | 不做"又一个能搜歌的 AI" | 同类 MCP 方案在 GitHub 上至少 10 个且免费，单做搜歌无竞争力 |
| 真实曲库作素材 | 曲库是教学的例子，不是卖点 | 教学类竞品普遍不接曲库，这是差异点 |
| 记忆归用户 | 记忆存本地，可导出可审查 | Spotify 与 Playtime 的记忆都在其服务端 |
| 中文 | 术语、讲解、曲库都面向中文用户 | 对标产品均为英文 |

竞品分析详见飞书文档《音乐类 AI Agent 竞品分析与需求可行性评估》。

## 2. 架构分层

```
src/
├─ theory/            乐理引擎：纯函数，零外部依赖，不引用 DSH
│  ├─ note.ts         音名模型、解析、等音处理
│  ├─ interval.ts     音程计算
│  ├─ scale.ts        音阶与调式推导
│  ├─ chord.ts        和弦构成与转位
│  ├─ key.ts          调号与五度圈
│  ├─ exercise.ts     练习题生成
│  └─ vocabulary.ts   受控词表（中文术语 ↔ 内部标识）
├─ audio/             音频：合成纯函数 + 播放 I/O
│  ├─ synth.ts        音符 → PCM 样本（纯函数）
│  ├─ wav.ts          PCM → WAV 字节流（纯函数）
│  └─ player.ts       写文件与调用系统播放器（唯一有 I/O）
├─ gateway/           曲库接入（可替换）
│  ├─ music-gateway.ts
│  └─ mock-music-gateway.ts
├─ tools/             DSH 工具封装：把下层能力暴露给模型
├─ memory/            用户画像与学习记录（阶段 2）
├─ dsh-plugin.ts      插件注册
└─ smoke.ts           确定性检查
```

### 分层铁律

**`theory/` 不得引用 `@deepseek-ai/*`、不得引用 `gateway/`、不得有 I/O。**

理由：乐理有唯一正确答案，必须能脱离 DSH 独立验证。一旦这层混入运行时依赖，正确性就无法单独测量。

**`audio/` 中只有 `player.ts` 允许有 I/O。** 合成与编码是纯函数，因此波形属性（频率、
包络、削波、WAV 头）可以自动验证；只有"声音好不好听"必须人耳判断。

**`tools/` 是唯一知道 DSH 存在的地方（除 `dsh-plugin.ts`）。**

## 3. 本阶段目标

### 做什么

第一批乐理确定性工具，全部为纯函数，不经过模型推理。

**为什么不让模型算：** 乐理计算有唯一正确答案，模型会在细节上出错（尤其是音名拼写与调号）。乐理算错会直接摧毁教学信任。纯函数同时消除三个问题：算错、耗 token、题目枯竭。

设计参照 Playtime 的公开说明：练习题由乐理规则生成，而非预录题库，因此不会用完。

### 不做什么

以下项在本阶段**明确排除**，防止范围蔓延：

| 不做 | 原因 | 何时考虑 |
|---|---|---|
| 音频合成、听辨发声 | 需要音频栈，独立课题 | 引擎稳定后 |
| 五线谱渲染 | 需 DSH 客户端插件层，API 未确认 | 摸清 API 后 |
| 乐器指型（吉他品位、钢琴手位） | 依赖用户乐器信息，见第 8 节 | 乐器确定后 |
| 播放、登录、收藏、建歌单 | 副作用操作，一直在排除范围内 | 暂不考虑 |
| 真实曲库接入 | 等开放平台凭证 | 凭证到手 |
| 创作、生成 | 版权诉讼环境未明 | 待法律环境明确 |
| 游戏化 XP / 连胜 / 对战 | 自用项目，收益低 | 可能永不 |

## 4. 乐理领域模型

### 4.1 音名表示：字母 + 变化音，不用纯半音数

这是整个引擎最关键的设计决策。

**错误做法**：用 0-11 的半音值（pitch class）表示音。这会导致 G 大调第七音输出 `Gb` 而非 `F#`，或 C 大调出现 `B#`。

**正确做法**：

```ts
type Letter = 'C' | 'D' | 'E' | 'F' | 'G' | 'A' | 'B'
type Accidental = -2 | -1 | 0 | 1 | 2   // bb, b, 本位, #, ##

interface Note {
  letter: Letter
  accidental: Accidental
  octave?: number        // 可选，缺省表示不限定八度
}
```

半音值由 `letter + accidental` 推导，而不是反过来。

**推论：音阶推导必须按度数走。** 大调、小调及教会调式的七声音阶中，七个字母各出现一次。算法从主音字母开始按字母序推进，用变化音修正到目标半音数。这样自然保证拼写正确。

### 4.2 音程：度数 + 性质

音程不能只用半音数表示，因为增四度与减五度半音数相同但功能不同。

```ts
type IntervalQuality = 'diminished' | 'minor' | 'perfect' | 'major' | 'augmented'

interface Interval {
  number: number              // 度数，1 = 同度，8 = 八度
  quality: IntervalQuality
  semitones: number           // 派生值
}
```

### 4.3 音阶与调式

第一批支持：

| 内部标识 | 中文术语 |
|---|---|
| `major` | 自然大调 |
| `natural-minor` | 自然小调 |
| `harmonic-minor` | 和声小调 |
| `melodic-minor` | 旋律小调（上行） |
| `dorian` | 多利亚调式 |
| `phrygian` | 弗里吉亚调式 |
| `lydian` | 利底亚调式 |
| `mixolydian` | 混合利底亚调式 |
| `locrian` | 洛克里亚调式 |
| `major-pentatonic` | 大调五声音阶 |
| `minor-pentatonic` | 小调五声音阶 |

### 4.4 和弦

第一批支持三和弦与七和弦：

| 内部标识 | 中文术语 | 音程结构 |
|---|---|---|
| `major` | 大三和弦 | 大三度 + 小三度 |
| `minor` | 小三和弦 | 小三度 + 大三度 |
| `diminished` | 减三和弦 | 小三度 + 小三度 |
| `augmented` | 增三和弦 | 大三度 + 大三度 |
| `major7` | 大七和弦 | 大三和弦 + 大七度 |
| `minor7` | 小七和弦 | 小三和弦 + 小七度 |
| `dominant7` | 属七和弦 | 大三和弦 + 小七度 |
| `minor7flat5` | 半减七和弦 | 减三和弦 + 小七度 |
| `diminished7` | 减七和弦 | 减三和弦 + 减七度 |
| `sus2` | 挂二和弦 | 纯四度 + 大二度 |
| `sus4` | 挂四和弦 | 纯四度 + 大二度（转位视角） |

转位以 `inversion: 0 | 1 | 2 | 3` 表示（0 为原位）。

### 4.5 受控词表

**为什么必须有：** 若模型今天说"忧郁"、明天说"emo"，记忆无法聚合，推荐无法对齐。所有领域概念必须映射到固定标识。

`vocabulary.ts` 负责双向映射：中文术语 ↔ 内部标识。工具输出同时返回两者 —— 内部标识供程序使用，中文术语供展示。

情绪与场景词表（供曲库检索用）同样固定，在此文件统一维护。

## 5. 工具清单

本阶段新增工具，全部只读、无副作用、确定性。

| 工具名 | 输入 | 输出 |
|---|---|---|
| `get_scale` | `tonic`、`mode` | 音名序列、级数、调号 |
| `get_chord` | `root`、`quality`、`inversion?` | 音名序列、音程结构、和弦符号 |
| `get_interval` | `from`、`to` | 度数、性质、半音数、中文名 |
| `get_key_signature` | `tonic`、`mode` | 升降号数量与具体音名、关系调 |
| `get_circle_of_fifths` | `key?` | 五度圈位置、相邻调、关系大小调 |
| `generate_exercise` | `type`、`difficulty`、`seed?` | 题目、选项、正确答案、讲解 |
| `play_notes` | `notes`、`style?`、`bpm?`、`octave?` | 播放状态、音名、频率、时长 |

`generate_exercise` 是把上面五个纯函数组合成练习题的生成器，对应 Playtime"规则生成而非题库"的做法。

`play_notes` 只做成一个工具而非 `play_scale` / `play_chord` / `play_interval` 三个：
音名序列已能表达全部场景，多余的工具只会占用上下文预算。

## 6. Agent 身份（阶段 1，与本批并行）

当前 Agent 使用 DSH `standard` preset，官方描述为"功能完整的编码 Agent"，挂载 bash、pwsh、文件读写、文件检索、子代理、工作流等工具。

**问题**：几十个无关工具的 schema 占用上下文与 KV cache；Agent 持有 Shell 与文件系统权限，对音乐场景既是噪音也是风险。

**方案**：在 `$DSH_HOME/.agent-presets/` 下建立音乐专用 preset，只挂音乐工具与必要通用工具（如 `ask_user`），并在 `cordis.patch.yml` 中把 `agent-presets` 的默认值指向它。

## 7. 记忆结构（阶段 2 预留）

设计原则：记忆是结构化数据，不是对话摘要。

首批字段按重要性排序 —— 前三项决定所有教学输出的形态：

| 字段 | 来源 | 用途 |
|---|---|---|
| `instrument` | 用户声明 | 决定谱号、讲解视角 |
| `level` | 测评 + 练习结果推算，非用户自填 | 决定内容深度，跳过已掌握内容 |
| `goal` | 用户声明 | 决定教什么、不教什么 |
| `masteredConcepts` | 练习通过记录 | 避免重复教学 |
| `weakPoints` | 错题聚合 | 针对性出题 |
| `tastePreferences` | 采纳/跳过反馈 | 推荐对齐 |

参照 Playtime 的两条做法：入门测评定位起点，表现好自动升级；所有内容按用户实际演奏的乐器调整（中提琴中音谱号、长号低音与次中音谱号、钢琴双谱表）。

存储走 DSH `storage-json`（落在 `$DSH_HOME/storages`）。

## 9. 验证方式

乐理有唯一正确答案，因此正确性必须可测量。

按既有约定不引入单测框架，扩展 `smoke.ts` 做确定性检查，覆盖易错场景：

| 检查项 | 期望 |
|---|---|
| G 大调音阶 | 第七音为 `F#`，不是 `Gb` |
| C♯ 大调音阶 | 出现 `B#`，七个字母各一次 |
| 降号调音阶 | 如 Eb 大调为 `Eb F G Ab Bb C D` |
| 增四度与减五度 | 半音数同为 6，但度数与性质不同 |
| 和声小调 | 第七音升高，A 和声小调第七音为 `G#` |
| 和弦转位 | 转位后音名集合不变，排列改变 |
| 减七和弦 | 四个音等距，含减七度而非大六度 |
| 五度圈 | C 的相邻为 G 与 F，关系小调为 a 小调 |

每次改动 `theory/` 必须跑 `pnpm run smoke`。

## 10. 决策记录

| 决策 | 理由 |
|---|---|
| 乐理用纯函数，不用模型 | 唯一正确答案；模型易错；省 token；题目无限 |
| 音名用字母+变化音，不用半音数 | 保证拼写正确，避免 C 大调出现 `B#` 类错误 |
| `theory/` 零依赖 | 正确性可独立验证 |
| 教学优先于曲库 | 教学不依赖凭证，且是差异点所在 |
| 保留 `MockMusicGateway` | 无凭证、断网时仍可开发与验证 |
| 不抄 Playtime 的产品形态 | 它是练习 app，我们是对话主导，形态不同 |
| 抄 Playtime 的引擎与水平自适应 | 这两点是被验证过的正确做法 |
| 练习生成接受 seed | 同 seed 必得同题，练习可重做、测试可稳定 |
| preset 模板存 `presets/`，由脚本同步 | `$DSH_HOME` 是生成状态不进 git，模板留在仓库才可重现 |
| persona 在两处维护 | web profile 走 preset persona，CLI profile 走 host system-prompt，无法跨文件引用 |

### 音频输出的技术选择

| 决策 | 理由 |
|---|---|
| 不用原生音频绑定（speaker 等） | Windows 上需编译工具链，易失败 |
| 不用 Web Audio API | 需客户端插件层，且 CLI 模式无浏览器 |
| **WAV 文件 + 系统播放器** | 零依赖；服务跑在本机，服务端出声即用户听到 |
| 加法合成（基频 + 5 阶泛音） | 纯正弦太单薄，分辨和弦性质更困难 |
| 包络含 8ms attack / 30ms release | 波形从 0 突变会产生可听爆音，斜坡是必需而非修饰 |
| 叠加后归一化 | 四音和弦最易削波 |
| 丢弃超奈奎斯特频率的泛音 | 否则折返成噪声 |
| 播放进程 detached + unref | 阻塞整轮对话直到播完不可接受 |
| 路径经环境变量传给 PowerShell | 避免含空格或引号的路径拼进命令字符串 |
| 按内容哈希缓存 WAV | 同一和弦重复播放不必重新合成 |

### 调研中确认的 DSH 行为

这几条是实施过程中发现的事实，影响后续开发方式：

**`dsh-base` 不含任何用户界面入口。** 只挂 base 的 profile 会启动后挂住 —— 既无输出也不退出。
用户界面必须由 surface bundle 提供：`@deepseek-ai/dsh-web-app` 给浏览器界面，
`@deepseek-ai/dsh-headless` 给「答完即退」的一次性问答。两个 profile 的 bundle 顺序为
`dsh-base → surface bundle → dsh-music-agent`，本地插件必须在最后，否则 persona 会被
surface bundle 的默认值覆盖。

**patch 不存在的 row id 会被静默忽略，不报错。** 因此 `agent-presets` 这一行只在 web
profile 存在，同一份 `cordis.patch.yml` 打到 CLI profile 时安全跳过，两套 profile 可共用一份 patch。

**agent preset 是按会话延迟挂载的。** 没有活动会话时 preset 不会被加载，
即使 preset 里写了不存在的插件名也不会在启动时报错。推论：**preset 的正确性无法在
无模型凭证时验证** —— 必须实际创建会话。这是当前唯一未验证的环节。

**客户端插件通过 `/plugins/<id>/client.js` 提供，清单在页面的 `window.__DSH_BOOT__` 里。**
这是阶段 4 可视化组件的接入点。

### 端到端实测结果

经 `dsh:ask`（CLI profile）实测通过：

| 验证项 | 提问 | 结果 |
|---|---|---|
| 调用乐理工具 | G 大调有几个升号，第七个音 | 答 1 个升号、`F#`，并使用了 `get_scale` 返回的「导音」术语 |
| 拼写准确性 | C 减七和弦四个音 | 答 `C Eb Gb Bbb`，主动说明「第七音是 Bbb 而非 A」 |
| 极端调 | C# 大调音阶 | 答 `C# D# E# F# G# A# B#`，7 个升号，并指出与 Db 大调为等音调 |
| 出题不泄露答案 | 出一道难度 3 的音程辨识题 | 只给题干与四个选项，声明作答后再批改讲解 |
| 曲库检索 | 推荐适合通勤的轻松音乐 | 调用 `search_tracks`，返回命中项并说明只找到一首 |
| 不编造歌曲 | 帮我找周杰伦的歌 | 明确说未找到，未编造，并提出换关键词 |
| 主动播放 | 听听 C 减七和弦，再放 C 大三和弦对比 | 调用 `play_notes` 播放两个和弦，并给出听觉特征对比讲解 |

### 未验证

| 项 | 阻塞原因 |
|---|---|
| preset 是否正确挂载、工具集是否真的裁剪 | CLI profile 走 `dsh-base + dsh-headless`，不经过 agent presets；须在 web GUI 中创建会话才能验证 |
